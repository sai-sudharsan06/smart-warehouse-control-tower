### Module 2: Warehouse Structure Management (2026-11-19)
- `zones` (code, name, type) and `storage_bins` (zone, rack, level, blocked flag)
- Zone types: Receiving, Storage, Picking, Shipping, Quarantine, Damaged
- Bin codes generated by the system (`A-01-02`), never typed by hand
- Single bin or a whole rack/level range in one all-or-nothing transaction
- Screen: Warehouse structure

### Module 3: Inventory Management (2026-11-19)
- `stock` (quantity per product and bin) and `stock_movements` (ledger)
- Every stock change goes through one function (`post_movement`) that writes
  the movement and the stock change in the same transaction
- Movement types: goods receipt, putaway, transfer, goods issue, count
  adjustment (+/-); each records source, destination, quantity, user, time
- Stock status follows the zone type; only Unrestricted stock (Storage and
  Picking) is available. Quarantine and Damaged stock is never available.
- Checks: no negative stock, no moving more than is in the bin, blocked bins
  refused, quantities rounded to 3 decimals
- Ledger check: rebuilds stock from the ledger and reports any difference
- Screen: Inventory (overview, move stock, movement ledger)

### Module 4: Goods Receiving (2026-11-19)

- Putaway with a suggested bin: a bin that already holds the product, else
  the first empty storage bin
- Screen: Goods receiving

### Module 6: Stock Discrepancy Investigation (2026-11-19)
- `stock_counts`: physical (counted) quantity stored next to the system
  quantity at the time of the count, with difference in units and EUR
- Blind count screen: the counter does not see the system quantity
- A difference needs a reason from a fixed list
- Tolerance: within 5 % and 50 EUR, adjusted automatically; otherwise
  pending approval by a second person (four-eyes principle), with a
  required decision note
- Approval is refused if system stock changed since the count (recount)
- Adjustments are ledger movements (`ADJ_IN`/`ADJ_OUT`, reference `CNT-00001`)
- Investigation hints from the records (other bins holding the product,
  recent movements, unposted steps). Hints never name or blame a person.
- Inventory accuracy KPI: share of counts within tolerance
- Screen: Stock counts

### Module 7: Order Management (2026-11-19)
- `sales_orders` (`SO-00001`, customer, requested date, priority, status) and
  `sales_order_lines`
- Status flow: Open, Released, Picked, Shipped, or Cancelled (with reason)
- Availability to promise (ATP) = unrestricted stock minus quantity reserved
  by released orders; quarantined and blocked stock is never promised
- Release only if every line is available (no partial release); shortages
  named per product; the release takes the database write lock so two
  releases cannot promise the same stock
- Screen: Customer orders (order lines entered in an editable table)

### Module 8: Picking and Route Optimisation (2026-11-19)
- Pick lists for released orders: bins chosen Picking zone first, then the
  bin with most stock; stock already planned for other open pick lists is
  not allocated twice
- Walking route optimised with Google OR-Tools (travelling salesman with a
  depot) and compared with bin-code order; tests check that OR-Tools finds
  the exact shortest route on small random cases (brute force)
- Simplified layout model, stated on screen: one aisle per storage zone, a
  front cross-aisle, 2.5 m per rack, level ignored. Distances are simulated.
- Confirm picking moves stock to a Shipping bin (`PICK` movements); shipping
  posts goods issue (`GI`) and closes the order
- Cancelling an order deletes its open pick list
- Screen: Picking and shipping (pick list, route chart, savings KPI)

Route model update: front and rear cross-aisles. With only a front aisle,
bin-code order was always already optimal (0 % saving in the demo data).
With both, OR-Tools saves 4.9 % walking distance over 622 simulated pick
lists in the demo data versus bin-code order (simulated layout, seed 42).

### Modules 9 and 10: Inventory Optimisation and Demand Forecasting (2026-11-19)
- Weekly demand from goods issues over the last 26 weeks
- Forecasts: 4-week moving average and exponential smoothing (alpha 0.3);
  the method with the lower mean absolute error on the history is used
- ABC analysis by annual consumption value (A up to 80 %, B up to 95 %)
- Safety stock z x sigma x sqrt(LT), reorder point, EOQ; service level by
  ABC class (98 / 95 / 90 %)
- Replenishment proposals when inventory position is at or below the
  reorder point (suggestions for a planner, not automatic orders)
- Assumptions listed on screen (normal demand, fixed lead time, assumed
  order and holding costs, no open purchase orders)
- Screen: Inventory planning (proposals, ABC Pareto, demand and forecast)

## Known limitations
- **No real login.** The "current user" is typed in the sidebar and is not
  authenticated. Real systems take the user from the login.
- **Unit cost is stored as a floating-point number (REAL)** and rounded to
  2 decimals. Enterprise systems use exact decimal types for money.
- **Product creation is not in the change history** (only edits are).
  `created_at` records when, but not who.
- **Products cannot be deactivated from the screen yet.** The `is_active`
  column exists, but no screen uses it.
- **Search treats `%` and `_` as wildcards** (SQL `LIKE` behaviour).
- **After renaming a product, the edit dropdown shows the old name** until the
  next click. The database and the product table are correct immediately.
- **Timestamps are stored in UTC** and shown in UTC (one hour behind German
  winter time).
- **Changes made before the change history existed are not recorded.**
- **After pulling new code, restart Streamlit** (Ctrl+C, then
  `streamlit run app.py`). A running server can keep old code in memory.
- **Bin capacity is not modelled.** Putaway suggestions ignore size and weight.
- **Partial delivery is not supported.** An order is released only when every
  line is fully available.
- **Partial picking is not supported.** All tasks of a pick list are confirmed
  together; one pick list per order (no batch picking of several orders).
- **Purchase orders are not modelled.** The demo generator simulates suppliers
  with its own simple reorder rule; the app only proposes quantities.
